- v2 首请求工具数量分布为 0 个 × 10、1 个 × 12、2 个 × 2、3 个 × 1；v3 为 7 个 × 25。

## 3. 方向：按 token 预算触发，而非固定 12 items

建议采用。模型容量大时，少量对话就滑动窗口会丢失可保留的原始上下文，也频繁改变历史前缀。
在预算内保留原始历史并只追加，达到阈值才压缩，更适合此项目的连续复盘。
这能减少截断丢失信息的机会，但不保证更长输入必然提高推理质量；仍需以真实任务质量和延迟验证。

核查时 DeepSeek 官方页面列出 `deepseek-flash` 的 context length 为 1M。
自定义 endpoint 可能有额外限制，应使用实际 endpoint/model 的有效容量配置，而非对所有模型
硬编码 1M。[官方模型说明](https://api-docs.deepseek.com/quick_start/pricing/)

### 建议的最小预算规则

- C：当前 endpoint/model 的有效上下文总预算。
- T：即将发送的总输入估计，包含固定 instructions、工具定义、输出 schema、历史、本轮快照、
  用户问题以及当前 run 已追加的工具结果；缓存命中的 tokens 同样占上下文容量。
- R：本轮输出（含适用的 reasoning）、工具往返增长和估算误差的预留。
- 当 `T >= min(0.9 × C, C - R)` 时，在可安全切分的边界执行压缩。

90% 是可配置的起始软阈值，不是 Provider 承诺，也不是让请求超过限制后再补救。若 R 超过 C 的
10%，应更早触发。小模型尤其不能只用百分比。输出上限还应与预算一致，不能将厂商的最大输出
默认当成每次教练回答需要的输出量。

例如仅作配置演示：C=1000000、R=100000 时约 900000 触发；压缩后目标可先设为不高于
约 60% C。60% 是待验证的上限目标，不是必须填满的长度：摘要 + 足够近期完整交互可能远小于此值。
一次留出较大余量，避免压到 89% 后下一轮再次压缩。

### 计数与触发时机

优先使用匹配模型的 tokenizer 或可靠的 Provider 计数能力；没有时采用保守估算，并用单次响应的
实际 input_tokens 校准。不能把一个 run 多个请求相加的 usage.input_tokens 当作当前窗口长度。
需要在发送前估算，而不只在收到 response 后检查；大工具结果也会让 run 中间增长。

初步实现可在用户 turn 开始前压缩，预留有界工具增长；每次模型调用前检查剩余容量。
若实际工具结果超出预留，需要在完整工具往返边界处理，不能发送已超限输入或拆断 call/output。

### 压缩内容与持久化

压缩后的模型输入建议为：固定 instructions → 一份连续性摘要 → 保留的近期完整交互 →
本轮权威快照 → 本轮问题。两次压缩之间原样追加，不每轮重写摘要或清理旧快照。

- 保留用户目标、约束、未解决问题、已讨论位置与合法引用，以及近期必要工具往返。
- 当前 FEN、评分、合法性、分类继续以最新快照和本次工具结果为准；摘要不升级为 Engine facts。
- 在完整 turn/tool-call 链边界裁剪，避免孤立的 function_call_output。
- 压缩结果、已覆盖历史边界需要一起持久化，受现有 generation/cancel guard 保护；失败时不能先删
  原始历史。原始会话可保留本地作为恢复来源，模型窗口从压缩 checkpoint 之后读取。
- 若无法生成有效压缩且剩余容量不够，应明确返回可操作错误，不发送超限请求；Engine Review 保持可用。

当前 `ConversationSummaryBuilder` 只是确定性截取最后用户消息、最后教练文本和少量问题，总长
1500 字符；它不是面向接近 1M tokens 历史的语义摘要。不能只把触发条件改为 90%，然后把大量历史
直接送进这个截取器。正式实现需要同时设计保留信息的压缩方式；若用模型摘要，应计入成本/延迟，
约束它只做连续性摘要，且失败不破坏原始会话。

实现边界：runtime 的 SessionSettings、GenerationGuardedSession 的读取上限、service 的摘要触发
与 checkpoint 必须同步调整。service 中用于短程指代解析的 recent_items 查询可以保持独立有界，
不能误当成模型历史窗口；max_turns/max_tool_calls 是单 run 执行预算，也不应随历史窗口取消。

## 4. 下一次验证

固定 endpoint、模型标签、工具/schema、问题序列和冷暖条件，分别记录首请求与后续请求。
加入真实连续多轮会话的评估场景，覆盖超过 12 items 但远未接近 token 上限、接近压缩阈值、压缩后
追问、局面切换和取消/失败恢复。边界行为可用较小的测试预算验证，不必消耗近 1M tokens。
真实长输入性能仍需另行测量，小预算只验证控制流程。

比较压缩次数、历史首次分歧位置、hit/miss tokens、每个成功回答的成本、延迟，以及事实/指代/
未解决问题保留情况。目标是在足够容量内减少不必要的信息损失和前缀变更，不仅是提高命中率数字。
