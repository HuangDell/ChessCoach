# 工具编排与 RAG：近期实施路线

日期：2026-09-13。状态：计划；本文没有新增运行能力或产生实验结果。

目标是在当前单 Agent 上完成“分析局面 → 识别教学需求 → 检索适用知识 → 给出有来源的解释与练习建议”。
先测工具编排，再测知识检索，最后测按需检索，分别回答决策、召回和教学收益的问题。
按单人约 13–18 个有效工作日安排；资料核验、模型下载和真实调用排队可能延长周期。

本路线是[原编排研究计划](execution-aware-tool-orchestration-plan.md)的近期交付切片，并增加 RAG。
它不等同于原计划 P2 所有方法与论文复现的完成。第一轮使用原生能力、一个运行时和本地索引；
多 Agent、大规模工具库、模型训练及跨任意棋局的自主导航留待后续真实需求。

## 当前起点

- 生产每次注册全部七个领域工具，并已有预算、作用域、generation、Grounding 和会话提交检查。
- [P0](../../tests/evals/orchestration/README.md)已有 24 个开发任务、30 个状态变体、状态投影、
  scorer、回放和 SDK + fake model 接线；当前 runner 明确拒绝 `live-fixture` / `engine-system`。
- `routing.py` 的候选提供器目前是固定/预设序列；动态候选接线不等于学会了根据执行结果选择工具。
- P0 task 合同的 split 当前仅接受 dev，正式测试集须新增版本化合同，保留冻结的 v1 fixture。
- `lookup_opening` 只查本地开局元数据；当前未实现文档 RAG。RAG 首先接入 Ask Coach。
- 已有 bounded Explanation 继续独立运行；当前棋局分析、学习 observation 和训练判定保持原事实边界。

## 四个交付阶段

| 阶段 | 粗估 | 实现与实验 | 完成产物 |
| --- | --- | --- | --- |
| M1：编排基线 | 2–3 天 | 复核 P0，增加真实模型 + fixture 工具的研究入口，冻结原生七工具基线和测试划分。 | 可复跑基线、逐任务轨迹、失败分类、成本与延迟报告。 |
| M2：执行结果驱动编排 | 3–4 天 | 比较全部工具、初始问题选工具、根据实际结果更新候选；检验依赖、恢复、复用和停止。 | 方法对照、配对状态实验、最小消融和适用边界。 |
| M3：教学知识检索 | 4–6 天 | 核验资料、语义分块、BM25 基线、向量召回与 RRF 融合，独立评测检索。 | 版本化小型语料、可重建本地索引、检索报告及引用合同。 |
| M4：按需检索与产品验收 | 3–4 天 | 接入一个知识检索工具，对比固定检索与按需检索，完成引用展示、异常路径及真实场景评估。 | 可演示功能、分层评测报告、关键失败轨迹和复现命令。 |

阶段可各自形成一次可审查提交。M2 未取得收益也应完成报告，以开发集选定的可靠基线继续 M3/M4。
以上天数合计为 12–17 天，另预留约 1 天整理报告；正式排期以 M1 的实测成本及标注速度调整。

## M1/M2：先把工具编排测清楚

任务围绕当前明确选中的局面，不要求工具具备尚未实现的跨棋局加载能力。组合示例：

> 比较当前局面的两种合法候选着法，结合我的历史弱项挑选练习；证据不足时说明缺口。

纳入已有事实足够、缓存缺失、非法候选、画像不足、候选为空、可恢复超时、预算不足和局面切换。
训练草案必须依赖成功返回且仍有效的候选；模型不能自行生成候选 ID 或升级用户弱项。

三个方法共用模型、任务、可执行权限、参数校验和预算：

| 方法 | 候选决策的输入 | 目的 |
| --- | --- | --- |
| A：全部工具 | 原生工具集合 | 测当前基线。 |
| B：初始问题选择 | 用户问题 + 初始 checkpoint | 测一次选择能否覆盖后续需求。 |
| C：执行状态选择 | B 的输入 + 已发生的工具结果、失败和剩余预算 | 测实际返回提供的增量。 |

B/C 先采用可审查的简单规则作为状态策略基线，不声称算法创新。复用现有候选接口，按 state revision
更新 snapshot；补充必要的有界 observation 字段，不能直接读 fixture/gold 或未来结果。
若后来使用 embedding/模型选择器，必须单列相对规则基线的结果及额外开销。

重点用同问题、同调用前缀而返回不同的配对任务验证下一步决策，例如“候选非空可建草案 / 候选为空
应结束或说明缺口”。无工具时是否正确停止同样计分。初始缺失信息只从当前状态产生，不抄 gold。
候选相关性与执行权限分开，所有方法的硬权限和前置条件一致；固定模型可见上下文，先隔离候选
策略的影响。再通过移除结果内容、仅保留错误码的消融判断是哪类信息起作用。

复用当前 4 turns / 6 tool calls / 2 Engine calls / 120s 作为首轮预算。复杂组合若不可在该预算下完成，
单列共同的研究预算档，不只放宽某个方法。记录被拒绝的尝试、逻辑调用及实际 Engine 次数。

验收以端到端完成、正确产物与事实核验为主；报告冗余调用、正确恢复/降级、过早停止、输入/输出
tokens、请求数、p50/p95 和超时。新增规划/检索请求也计入总量。七工具无收益是允许的结果。

## M3：构建有教学用途的 RAG

第一轮聚焦 `calculation.exchange_sequence`、`tactics.loose_piece_awareness` 和
`calculation.opponent_forcing_moves`。先做约 20 个经核验的知识段落贯通链路，再按覆盖缺口扩充至
约 80–120 段；数量只是工作量目标，不代表足以证明大规模检索能力。

资料优先采用自己整理且经棋理核验的说明，以及许可明确的公开教材/文章。模型草稿须人工核验后
才可入库；不能把现有生成讲解自动当作权威教材。知识单元保留“原则、适用条件、例外和例子”，
按教学段落切分，避免把例外条件切到另一段。较长条目再按句子边界拆分，记录父文档位置。

最小元数据：`doc_id`、`chunk_id`、标题、正文、章节/段落位置、来源及许可、内容版本/hash、
语言、教学主题和适用条件。有棋例时保留例子的 FEN 和可重放着法，不能当成用户的当前局面。
原文可用于引用核对；检索索引可由源资料与冻结配置重建，更新采用完整快照原子替换。
用户导入资料与生成索引位于 `<DATA_DIR>/knowledge/`；仓库仅保留可发布的小型 fixture。

实现顺序为 BM25 → 固定 embedding 的向量召回 → RRF 融合。小语料在进程内检索即可，不增加独立
向量数据库服务。固定中文分词、英文棋谱符号处理、embedding 版本/归一化和 chunk 版本。
原始 FEN 不直接作为语义查询；使用用户问题及已验证 facts 的教学主题构造查询。主题优先作为
排序线索，避免错误硬过滤把相关材料完全排除；所有对照使用相同过滤规则。

检索实验固定查询集，比较 Recall@5、MRR@5 和延迟；标注可接受段落集合与分级相关性。
无答案查询不混入正例 Recall 分母，另报误返回及正确不回答的比例。相似度/RRF 分数不是置信概率，
不能用一个通用阈值宣称资料适用性；必要的阈值只在开发集校准。
只有召回已覆盖而前列排序仍是主要瓶颈时才增加 reranker，并单列收益与代价。

候选新工具为 `search_coaching_knowledge(query, skill_ids, limit)`，第一版只增加这一个稳定能力。
返回有界段落、来源引用和 `found/no_match/unavailable` 等明确状态。引用须绑定 corpus version、
doc/chunk ID 与返回内容；`found` 只表示检索有候选，不认证自然语言结论正确。

## M4：让编排决定何时检索

希望形成的产品行为：

```text
当前局面/目标 → 复用或补充 Engine facts
             → 若需要一般教学知识，查询资料；若已有足够依据，直接解释
             → 引用资料说明原则，并结合当前 facts 说明适用范围
             → 若用户要求练习，按画像与真实候选形成草案
```

比较三个条件：无知识检索、固定在回答前检索一次、Agent 按需检索。固定 M3 选出的检索器、
M2 选定的编排策略、语料和预算；不同阶段的实验分别报告，不能把所有改动的增益归给动态编排。
固定预检索也计入调用和上下文预算。按需模式首版最多两次检索，第二次仅针对明确缺口，
新查询和返回都进入现有 run 预算；重复查询计入冗余调用。

对只需 Engine facts 的问题检查是否产生无用检索；对资料覆盖的问题测回答与引用；对不覆盖的问题
测不虚构来源和正确表达不足。无 RAG 正确说明缺资料算协议正确，不能算知识任务完整成功。

新增知识引用使用独立字段/类型，不混入棋局 evidence 命名空间。只允许引用本次上下文或成功工具
实际提供的知识段落。程序检查来源、版本和引用范围；段落是否支持正文及原则是否适用于该局面，
另做内容评价。具体合法性、评分、分类和个人弱项仍由原有 Core/facts/observation 判定。
知识文本不能被解释为工具授权或系统指令；来源缺失、过期或服务不可用保持明确降级。

同步工具 registry、DTO、prompt、响应校验、版本和前端引用展示；旧会话新增可选字段默认空。
七工具冻结实验继续保留，加入知识工具后的 registry/dataset 使用新版本，避免改写历史基线。
旧 analysis/explanation/attempt/learning 不迁移为知识存储。前端沿现有 API 和 feature 边界接入。

## 数据、评价与执行预算

- P0 的开发样例继续做开发/回归；正式 held-out 测试另建，按源棋局和近重复任务分组。相同局面的
  改写不能分别进入开发与测试。查询模板、gold 答案与 scorer 标签不进入候选提供器。
- RAG 测试文档可合法存在于检索库，测试问题/标注不能用于调参；来源相同或近重复的文档形成分组。
  普通检索效果与未见来源上的迁移效果单列，不能把相同资料的改写当独立泛化证据。
- M1 先选约 8 个开发场景做 live pilot，冻结明确的请求/token/时间上限后执行，依据实测决定正式
  运行规模；预算未确定不启动完整付费矩阵。失败和重试全部计入，缺失 usage 不记为零。
- 正式比较固定版本，交错运行方法，至少 3 次重复作为初步稳定性检查。报告逐任务配对差异及按
  源棋局/任务组统计的不确定性；重复采样不增加独立任务数，不把小样本 p95 当线上性能承诺。
- 分别报告候选/段落检索、端到端任务、结构化校验、正文质量和成本。终态拒绝或丢弃输出仍计入
  失败，避免仅统计通过验收的回答获得满分。
- 正文按冻结 rubric 检查事实错误、引用支持、适用条件和可操作性，隐藏方法标签做人工配对评价；
  至少对部分样例由第二位检查者复核。模型 judge 可辅助，不能冒充独立人工评价。
- 开发集结束时冻结质量非劣容忍度和最低有意义的成本收益。正文质量、事实边界、成功率有明显
  回退则保留原策略；不确定时继续实验，不把“代码可运行”当作生产收益。
