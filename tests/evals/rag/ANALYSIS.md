# RAG Benchmark 现状分析（2026-09-14）

本文保留实施前的缺口分析。后续已完成 v3 标签迁移、真实索引与检索 runner，
并进行 sub-agent 模型辅助补审；最新状态和结果见 [RESULTS.md](RESULTS.md)。

这套 40 条数据目前是可校验的候选集，还不是可发布质量分数的 Benchmark。
Agent 26 条 portfolio 使用 fixture tools，即使模型调用知识工具，也不能证明真实检索有效。
两套评测分别运行、分别出报告；本次只整理目录和分析，不执行 embedding 或外部模型调用。

## 已有基础

- 查询与 gold 分离，具备中文问题、英文参考译文、答案要点、相关性等级、来源 hash 和概念分组。
- 40 条包含 22 条通用棋理、12 条合成局面、2 条用户 FEN 问题、2 条缺失来源上下文、2 条语料外问题。
- 冻结 v2 corpus 来自两本英文教材，共 444 chunks；14 个局面与 82 处来源引用可确定性校验。
- `validate_dataset.py` 只读取显式数据路径，检查身份、来源指纹、FEN/SAN、候选着及模型输入字段。
  自动化回归使用合成临时数据，不读取本地真实问题。
- 生产代码已有 dense + LanceDB FTS、双路各 20 候选、RRF k=60、按正文 hash 去重及最终最多 5 段。
  检索 trace 已可保留双路候选、融合排名和分阶段耗时，可复用作诊断依据。

## 必须先解决的缺口

### 1. 语料版本与真实索引（首要阻塞）

标注绑定 v2 的 444 段，当前生产 corpus 为 v3 的 670 段。生产
`load_corpus_snapshot` 要求当前版本，直接拿 v2 快照调用当前索引构建也会被拒绝；
CLI `index` 默认重建语料，会改变旧标签指向的分块。目录迁移不会解决这个问题。

建议保留 `zh-en-v1` 不变作为历史快照，为当前 v3 建立新数据版本：重新定位来源、复核
grade/答案要点并冻结指纹，不能只替换 manifest 的版本或 chunk ID。
尤其 D01/D02 的“缺图/棋谱”标签需要重审：v3 已保存图片和表格，但保存原图并不等于
检索或模型已获得可验证 FEN；应按实际可传给回答模型的材料判断证据是否足够。

使用独立评测 data directory 构建与标签严格匹配的索引，验证实际模型加载、一次查询及来源
fingerprint。此前本机检查只有模型文件和依赖，未证明 GPU/embedding 推理可用，也未发现
active generation；不要将“安装齐全”作为可开始质量评测的验收条件。

### 2. 独立检索 runner 与评分

目前只有完整性校验，没有批量检索、指标计算或运行报告。下一步 runner 应显式接收 dataset、
corpus/index 和 output 路径，先校验指纹，再保存每题查询、候选 ID、分数、排名、去重结果及耗时。
复用现有检索逻辑与 trace，避免在评测中复制另一套 RRF。BM25、dense、hybrid 对照使用
同一语料、同一查询、同一技能输入、同一 top-k 和明确的去重规则。

首轮固定参考英文译文，比较 @3/@5 的已知正例 Hit 与已知证据 MRR，并报告未判断候选比例、
逐题结果和类型分组。明确直接证据 grade=2 与背景 grade=1 的计分区别；缺图和语料外题不进入
普通正例召回分母。候选池标注完善后再给出 pooled Recall/nDCG，并注明判断池范围。
不得将未标注段落当作负例，也不能把这批不完整 qrels 的结果称为全库 Recall/Precision。

记录 dataset/corpus/index/model 指纹、代码版本、查询方式、参数、设备与冷启动/热查询耗时；
翻译、embedding、检索和生成分别计时。独立 BM25 延迟不能用先执行 embedding 的混合调用总时长代替。
报告写到 `reports/rag/<run-id>/`，错误和未执行项显式记录，不混入 Agent portfolio 指标。

### 3. 标注复核与防止测试泄漏

全部标签为 `draft_pending_human_review`、`qrels_complete=false`，参考译文也是助手草拟。
当前 80 条相关性判断为 57 条直接支持、20 条背景、3 条负例，覆盖 45 个不同 chunk；
另有 2 条诊断引用。负例覆盖偏少，尚不足以评估对相似但不支持问题的段落的区分能力。
需混合三种检索器的候选、隐藏来源系统和排名后进行独立人工复核，补充遗漏正例和难负例。
现有 validator 写死“必须待审且非穷尽”，正式标注完成时需要随数据版本更新状态契约和回归测试，
否则人工审核后的合法数据反而无法通过校验。

按概念和共享证据分组后再划分开发/测试；仅按现有 `group_id` 不足以排除不同组共享同一段落，
还需检查证据重叠与近似问法。40 条、两本历史教材只适合首轮诊断，不能推断广泛棋类问题表现。
先完成现有样本复核，再按失败类型补题；不要为凑规模直接扩大同源近似问题。

## 后续完整链路工作

1. **查询语言对照**：先测中文直检与固定英文参考查询，识别翻译收益。生产检索目前不自动翻译，
   因而英文检索成绩不能冒充当前生产端到端成绩。实际 LLM 翻译单独加入后，冻结/缓存输出以保证
   三路输入一致，记录模型、prompt 版本、usage、延迟及失败；只允许读取问题和已验证上下文，禁止 gold。
2. **回答与引用评价**：检索命中和回答正确分别评分。用独立答案 rubric 评价教学点、引用是否支持
   声明、是否虚构当前局面或个人弱项；需要分数/最佳着的题先补固定配置的 Engine facts。
   FEN 合法不等于棋理、胜负或最佳着已经验证。
3. **证据不足行为**：生产 `found` 仅表示存在候选，目前没有相关性拒答门槛。
   D/N 四题需要单独考察是否承认材料缺失、是否捏造 FEN/统计/Engine 分数。
   先记录失败再决定是否需要阈值或 reranker，不预先引入这些能力。

## 建议实施顺序与完成标准

先冻结并复核 v3 标签、验证独立真实索引；然后实现固定查询的三路检索 runner 和合成评分测试，
跑候选池诊断，完成人工补标及分组冻结；最后再做实时翻译和端到端回答评价。
索引准备与 runner 编写可以先推进，但正式质量结论必须等待标签和评分口径验收。

第一阶段交付应能复现 40 题每题的检索结果，定位空召回、错误召回和证据不足，
并清楚标明未判断结果及未执行项目。完整性校验通过、Agent 26 条通过或一次检索返回 `found`，
均不能代替这一标准。
